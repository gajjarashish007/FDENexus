# M03 Infrastructure as Code & Automation

The change engine behind every infrastructure request. It owns the Terraform component registry, renders Atmos stacks,
evaluates policy, estimates cost, validates with Atmos, routes approval, publishes to GitLab and tracks state versions.

## Layout
```
iac/
  atmos.yaml                      Atmos config; stack name = environment
  components/terraform/<name>/    12 components (validated with terraform validate)
  components/registry.json        version, status (active|deprecated), category, description
  stacks/catalog/<name>.yaml      org defaults (<name>/defaults, abstract)
  stacks/mixins/backend.yaml      S3 state, encryption, native lock files
  stacks/deploy/<tier>/<env>.yaml GENERATED by the portal after approval
  changes/<CHG-id>.json           GENERATED: operations to apply/destroy, in order
  scripts/run_change.py           executes a change manifest with atmos (CI and portal)
  .gitlab-ci.yml                  validate + plan on MR, apply after merge, manual for production
backend/
  engine.py   change lifecycle, rendering, conflicts, queue, GitLab publish, rollback, drift
  policy.py   16 policy-as-code rules (deny blocks, warn forces human approval)
  cost.py     monthly estimate from list prices
  gitlab.py   GitLab REST v4 client (token from GITLAB_TOKEN only)
  module.py   HTTP routes under /api/m03
```

## Change lifecycle
`propose` -> `blocked` (deny rule) | `pending_approval` | auto `approved` (low-risk non-production)
-> `queued` (another MR open for the environment) -> `mr_open` -> `merged` -> `applied`, or `committed` -> `applied` without GitLab.
Requesters cannot approve their own change. MR closed without merge restores the previous stack version.

## GitLab setup
1. Create a project (e.g. `platform/iac`) and copy `iac/` into it (keep `stacks/deploy` and `changes` empty).
2. Create a project access token with the `api` scope (Developer role). Export `GITLAB_TOKEN` before `./start-portal.sh`.
3. In the portal: IaC Changes, then GitLab & settings. Enter the URL and project, then click Test connection.
4. CI variables: `FDE_IAC_IMAGE` (image with atmos, terraform, python3, aws cli) and `CI_AWS_ROLE_ARN` (OIDC role).
5. Create the state bucket per account (`fde-nexus-tfstate-<account id>`, versioned, encrypted) before the first apply.

## Live mode
`./start-portal.sh --prod` turns simulation off. Plan from the portal needs AWS credentials on the host.
Portal apply is off unless `M03_PORTAL_APPLY=1`; the normal path is GitLab CI after merge.

## Capabilities
| Capability | Status | How |
|---|---|---|
| Terraform module registry | live | 12 components with parsed inputs, outputs, version and status. |
| Version-controlled infrastructure templates | live | Stacks are generated YAML committed to GitLab through merge requests (local files without GitLab). |
| Automated plan generation | partial | Every change runs atmos validate + describe. A real terraform plan runs in GitLab CI or in live mode. |
| Plan review | live | Reviewers see the YAML diff, policy findings, cost delta and validation output before approving. |
| Policy validation | live | 16 policy-as-code rules (deny blocks, warn forces human approval), mapped to CIS/NIST/ISO/SOC 2. |
| Security scanning | partial | Built-in rules always run; Checkov or Trivy run automatically when installed on the host or CI image. |
| Cost estimation | live | Monthly estimate from list prices per component; usage-based items listed as notes. |
| Deployment orchestration | live | One open merge request per environment, queue, ordered operations, GitLab CI plan/apply, manual gate for production. |
| State management | live | S3 remote state per stack and component, generated by Atmos. |
| State locking | live | S3 native lock files (Terraform >= 1.10) plus a CI resource group. |
| Drift detection | partial | terraform plan -detailed-exitcode per component; needs live mode and credentials. |
| Rollback and recovery | live | Roll an environment back to any stack version as a new reviewed change; closed MRs restore the previous stack. |
| Module versioning and deprecation | partial | Registry version and deprecated status are enforced on new changes; pinning multiple versions is not built yet. |
